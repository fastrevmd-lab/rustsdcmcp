# mecmcp 0.3.7 Adoption Design

Date: 2026-07-29

## Goal

Evaluate and, if every compatibility and packaging gate passes, adopt the
`changeset-v0.3.7` mecmcp tag across rustsdcmcp as one coherent dependency
update. Open a draft pull request after review.

This work does not implement the new shared change-set CLI. mecmcp documents
the flag names and high-level behavior but does not define precedence for a
consumer that already stores the same values in product configuration.
[mecmcp#162](https://github.com/fastrevmd-lab/mecmcp/issues/162) tracks that
missing standard. rustsdcmcp must not invent repository-local precedence while
that issue remains unresolved.

## Upstream boundary

The current source and package builder use `changeset-v0.3.6` at commit
`93ab63d7c2fad649112807378f92fcc26cce73c6`. The target tag is
`changeset-v0.3.7` at commit
`85137c509fe1803b87e8636462f0392ce05072ce`.

The upstream runtime change is additive:

- `ChangeSetOutput` gains an optional `approval_waiver` string.
- Ordinary two-person change sets omit the field.
- A waived lab-mode change set reports `approval_waiver: "lab-mode"` while
  keeping `approver: null`.
- The stored waiver already existed in `0.3.6`; `0.3.7` exposes it to callers
  rather than changing the persisted waiver representation.

The other commits after `0.3.6` and before the current mecmcp main branch are
test infrastructure, test utilities, or documentation. This adoption pins the
released `changeset-v0.3.7` tag, not mecmcp `main`.

## Dependency architecture

All five mecmcp dependencies move together:

- `mecmcp-audit`
- `mecmcp-auth`
- `mecmcp-changeset`
- `mecmcp-runtime`
- `mecmcp-transport`

Every manifest entry must use version `0.3.7` and tag
`changeset-v0.3.7`. Every mecmcp entry in `Cargo.lock` must resolve to the same
`85137c509fe1803b87e8636462f0392ce05072ce` commit. A mixed mecmcp version or
commit is a failed adoption.

The 59 temporary, issue-linked compatibility declarations remain unchanged.
`0.3.7` does not implement that compatibility ledger and does not clear the
stable-release blocker.

## Runtime behavior

rustsdcmcp preserves its current production-safe behavior:

- `ChangeManager` continues to load the coordinator with lab mode disabled.
- `prepare_sdc_policy_deploy` creates a plan that requires an independent
  approval.
- `approve_sdc_change_set` remains the only approval path.
- No waiver call or automatic approval is added.
- Normal change-set MCP output must not gain an `approval_waiver` field.

No SDC endpoint, payload, credential, tool scope, or write workflow changes in
this adoption.

## Persistence compatibility

A checked-in, synthetic `0.3.6` state fixture will prove the upgrade boundary.
The fixture must:

- be produced using the pre-upgrade `0.3.6` coordinator format;
- contain a non-terminal, ordinary two-person change set with synthetic tenant,
  owner, digest, fingerprint, and action data;
- contain no live tenant ID, credential, bearer token, HMAC key, API payload,
  device address, or runtime dump;
- be loaded by the `0.3.7` coordinator without rewriting it;
- return the same change-set identity, state, owner, digest, expiry, and action
  count;
- serialize without `approval_waiver`.

The compatibility test must fail if loading the fixture loses data, changes the
normal-mode output contract, or rewrites the file as a side effect of reading
it.

## Package and documentation boundary

Source-controlled metadata for future builds moves to
`changeset-v0.3.7`, including:

- the package builder's `BUILD-INFO` value;
- installer and smoke-test validation of `BUILD-INFO`;
- packaging-policy assertions;
- generic operations documentation;
- the README's source and future-package dependency statement.

Historical facts do not change:

- private prerelease `v0.1.0-lab.1` was built from source commit
  `65135e29484be4487f5ba58bdf70ec0ef7518288` with mecmcp
  `changeset-v0.3.6`;
- VMID 606 currently runs that `0.3.6`-based artifact;
- `docs/lab-deployment-606.md` remains the immutable acceptance record for
  that deployment;
- previously committed design and implementation-plan records are not rewritten
  to pretend they used `0.3.7`.

The README must distinguish the existing prerelease/deployment from the updated
source and next package build. This change does not create, replace, or promote
a release artifact.

## CLI standard blocker

This adoption must not add `--lab-mode`, `--state-file`, or
`--approval-timeout-secs`.

The later CLI subproject will follow the resolution of mecmcp#162 and the
existing mecmcp rules that are already settled:

- the three public flag names are identical on every server;
- lab mode is explicit, defaults off, warns at startup, and automatically
  waives approval at plan creation;
- waived output uses `approver: null` plus
  `approval_waiver: "lab-mode"`;
- no separate waiver tool is exposed.

Until precedence is standardized, `sdc.json` remains authoritative for
`changeset_state_file` and `approval_ttl_secs`.

## Verification

The adoption is accepted only when all of these pass:

1. a pre-change baseline build and all workspace tests on `0.3.6`;
2. dependency and lockfile assertions proving one `0.3.7` tag and commit;
3. the synthetic `0.3.6` persistence compatibility test;
4. the normal two-person output regression test;
5. `cargo fmt --all --check`;
6. `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings`;
7. `cargo test --workspace --locked`;
8. `scripts/verify-packaging.sh`;
9. a clean lab-package build and package smoke test;
10. inspection of the generated `BUILD-INFO` and CycloneDX SBOM for
    `changeset-v0.3.7` and the expected mecmcp components;
11. task-scoped review and final whole-branch review.

The package build remains local and commit-addressed. It is not uploaded or
deployed.

## Safety constraints

- Do not call any live SDC endpoint.
- Do not submit a preview, approval, deployment, or other mutation.
- Do not read or copy the external SDC credential.
- Do not modify VMID 606, DNS, systemd state, release assets, or GitHub
  releases.
- Do not modify mecmcp code; mecmcp standards work remains in mecmcp#162.
- Do not change the 17-tool surface.
- Do not open a non-draft PR.

## Failure handling

Stop the adoption and report the evidence if:

- any mecmcp crate resolves to another version or commit;
- `0.3.7` cannot load the `0.3.6` fixture exactly and read-only;
- ordinary output gains waiver metadata;
- build, Clippy, tests, packaging, smoke checks, or reviews fail;
- the update requires a CLI or runtime behavior decision reserved for
  mecmcp#162.

No compatibility failure may be papered over by editing the fixture or relaxing
an assertion after the version bump.
